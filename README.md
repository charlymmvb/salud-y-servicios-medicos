## FASE 1: Generacion de datos y modelo relacional

Para la generacion de datos aleatorios decidi implementar un dag, esto para simular un sistema legado del que se extraen los datos para depositarlos en storage, en formatos avro, parquet y csv.

El DAG cuenta con un unico job batch, que es el encargado de la generacion de los datos, disponible en data-generation\dag_ssm_genera_insumos\jobs\job_batch_ssm_generar_insumos.py
Los parametros para la generacion de datos se leen desde un archivo json ubicado en data-generation\dag_ssm_genera_insumos\jobs_config\config_job_batch_ssm_generar_insumos.json el cual contiene la semmila aleatoria parametrizable, con la que se busca garantizar que siempre se obtengan los mismos resultados al utilizar fake y np.random.

El proceso se baso en crear los dataframes en el orden de aparicion del documento, haciendo uno de numpy para datos que necesitaran distribuciones, spark para el manejo de datos y faker para la creacion de datos falsos, esta ultima se consulto en los siguientes portales:
* https://pypi.org/project/Faker/
* https://faker.readthedocs.io/en/master/providers/baseprovider.html#faker.providers.BaseProvider.random_element

Para la tabla PAC_REGISTRO el campo pac_id al ser un identificador se establecio como consecutivo, es decir, el primer registro obtuvo el 1, el segundo el 2, y asi sucesivamente. La fecha de nacimiento es un numero aleatorio, primero se calcula la edad de la persona siendo un numero aleatorio de entre 0 a 118 años (de acuerdo con la persona mas longeva registrada y que se puede atender personas con pocos meses de vida), siguiendo una distribucion normal con media de 45 años, debido a que a pesar de que la edad media de la poblacion en latinoamerica es de 30 años, conforme la edad aumenta muy probablemente tambien lo hagan los problemas de salud. (la informacion recopilada procede de https://www.eluniversal.com.mx/cartera/envejece-america-latina-cual-es-la-edad-media-de-los-latinoamericanos-y-cuantos-hijos-tienen/). En el caso de la ciudad se investigaron las ciudades de los 3 paises, se agregaron a un diccionario y se les asigno un ID, posteriormente para cada persona se eligio un numero aleatorio de entre las opciones.

El tip_doc se establecio como tipo de documento, es decir, el documento que se utilizara para registrar la identidad del paciente. Dado que la empresa opera en 3 paises diferentes, investigue los documentos de identidad aceptados por cada uno de ellos (disponibles en https://help.clearid.io/ES/R_CID_IdentityDocumentTypes.html), para la asignacion se realizo una validacion, buscando que el tipo de documento corresponda con la ciudad de residencia de la persona, y que las edades correspondieran, de esta manera no se podra tener una identificacion de menores para un mayor de edad, o una licencia de conducir para alguien con  años. Para generar el tipo de documento se utilizo fake, validando el numero de digitos que debia tener cada identificacion de acuerdo al pais, en el caso del pasaporte se utilizo la funcion de fake que permite generar pasaporte aleatorios. Una vez con el numero de documento, se implemento sha256 para obtener el hash para la columna num_doc_hash a traves de hashlib (https://www.w3schools.com/python/ref_module_hashlib.asp)

En el caso de los generos, se creo un diccionario ordenado que permitiera agregarles pesos, de esta manera fake puede escoger un elemento aleatorio de acuerdo con la probabilidad colocada, agregando tambien el valor de null en 5%, los pesos para masculino y femenino fueron 0.49 y 0.46 respectivmente, esas cantidades se decidieron de manera arbitraria.

Para el estrato socioeconomico tambien se creo un diccionario con pesos, basandome en https://repositorio.cepal.org/server/api/core/bitstreams/3694b22b-988f-4293-abba-ab4bcd4de42a/content los defini como:
* Estrato bajo       52.1%
* Estrato medio      44.5%
* Estrato alto        3.4%

Para la fecha de primera atencion se selecciono una fecha aleatoria utilizando faker, validando que esta fecha no pudiera ser anterior a la fecha de nacimiento del paciente o la fecha en que la empresa inicio operaciones en 1987.

Para la tabla MED_PLANTA el id_med se estalecio de manera consecutiva. En el caso de la especialidad, investigue la categorizacion de especialidades y subespecialidades en https://www.mineducacion.gov.co/1759/articles-403336_Documento_01.pdf para crear un diccionario que permitiera elegir una especialidad al azar y con base en eso una subespecialidad, aunque esta segunda podia quedar nula. Para la fecha de ingreso,calcule la edad del medico para que no pudiera tener menos de 25 años, que es la edad aproximada en la que se empieza a ejercer la medicina, y 75 años, que es una edad de retiro muy elevada, con base en esto elegi una fecha aleatoria y la compare contra la fecha de nacimiento del medico y la fecha de fundacion de la empresa para evitar fechas de ingreso cuando el medico tuviera corta edad o antes de que existiera la empresa. Para el tipo de contrato y jornada investigue los posibles valores.

Para la tabla RED_SEDES el id_sede se tomo consecutivo, el nombre de la sede tomo un nombre de la lista de ciudades aleatorio pero unico, con eso tambien se puede obtener el id_ciudad y el id_pais. el tipo de sede se calculo tomando en cuenta las restricciones de cantidad para cada tipo, se creo una lista que contuviera los distintos tipos por la cantidad de apariciones y se realizo un shuffle para que a cada sede le tocara uno aleatoriamente. Para la capacidad de camas, debido a una confusion de mi parte asumi que la empresaba contaba con 500 mil camas, por lo que realice una matriz de 84x4, cada fila representaba una sede y cada columna un tipo de cama, a continuacion llene la matriz con un ciclo for y numeros aleatorios considerando el numero de camas disponibles y casillas pendientes en cada iteracion buscando garantizar que cada tipo de sede tuviera al menos una cama de cada tipo. El nivel de complejidad se establecio de manera arbitraria, Alta complejidad para hospitales de alta complejidad, Mediana para clinicas de mediana complejidad y Baja para el resto. 

En el caso de la tabla HCE_ENCUENTROS, preferi orientarla principalmente a hospitalizaciones, porque en el primer acercamiento note que incluia campos de fecha de registro y fecha de egreso, por lo que decidi aprovecharla para guardar los registros en los que el paciente tuvo que quedarse en una de las camas, que posteriormente ayudaria a crear la tabla de camas. De esta manera, el id_encuentro quedo consecutivo al igual que los anteriores. Se establecio arbitrariamente que el 27% de los pacientes registrados tuvieran hospitalizacion en su primera atencion, por lo que se creo un ciclo desde 1 hasta esa cantidad colocando el tipo de consulta como primera vez, y luego se proceso el resto de registros para obtener la cantidad indicada para esa tabla, pero colocando el tipo de consulta como control. El metodo para primeras veces fue tomar pac_id aleatoriamente entre la lista de pacientes disponibles, luego se selecciono un medico cuya fecha de ingreso fuera menor a la fecha de primera atencion para ese paciente, con esto obtenemos id_sede tambien, despues, la fecha de inicio de atencion sera la primera atencion, se utilizo un random siguiendo distribucion exponencial para calcular un tiempo de espera tomando el promedio de 45 minutos indicado con un maximo de 4 horas, la distribucion exponencial se debe a que esto nos dara mayormente cantidades muy pequeñas, y muy pocas veces se acercara al pico de las 4 horas. Obtenemos la hora de registro restando el tiempo de espera a la fecha de registro y por ultimo obtenemos la fecha de egreso calculandola con fake entre la fecha de inicio de atencion y un limite arbitrario parametrizado de 15 dias. Como ya tenemos al medico podemos obtener su especialidad con un diccionario (las especialidades se obtuvieron de https://www.mineducacion.gov.co/1759/articles-403336_Documento_01.pdf) y el cie10 con otro diccionario al que se accede mediante la especialidad. En el caso de la especialidad y los codigos cie10 solamente se utilizo una muestra, debido a que los datos serian demasiados para copiarlos a mano (se obtuvieron de https://buscadorcie10.es/que-es-cie-10#estructura). Los procedimientos se encuentran tambien en un diccionario que para fines del ejercicio contiene unicamente un codigo por especialidad, ya que cargar todos necesitaria demasiado tiempo (los codigos se obtuvieron de https://www.cgcom.es/sites/main/files/files/2022-05/nomenclator.pdf). Con el codigo se puede acceder al costo del procedimiento o vr_facturado.

Para la tabla GCM_CAMAS que requiere 500 mil registros, se tomo en cuenta que cada registro tendra las metricas de camas para un tipo de cama a determinada hora en una sede, es decir, si tenemos 82 sedes, con 4 tipos de camas, en una hora tendremos 328 registros, asi que se divide el total de registros que necesitamos entre esa cantidad para saber cuantas horas necesitaremos. Con ese dato, establecemos la hora final como la hora en curso y la hora final como la hora en curso menos la cantidad de horas que necesitamos (cabe aclarar que esto se refiere al datetime completo y no solo las horas). Con esto, aprovechamos que en la tabla de sedes contamos con la informacion de cuantas camas tiene cada sede, asi que se puede crear un diccionario de capacidad maxima por sede para cada tipo de cama. Con un ciclo recorremos cada hora desde la hora inicial hasta la final buscando los encuentros activos, es decir, la cantidad de personas que estaban ocupando camas en una misma sede, se reparten los tipos de camas de manera aleatoria empleando el diccionario de capacidades y por cada paciente que se agrega a un tipo se descuenta 1 del total disponible, asi evitamos registrar mas camas de las que realmente existen para cada tipo. Las ocupaciones se guardan en un diccionario aparte, al final se obtiene la capacidad total y las ocupaciones para esa sede en esa hora, asi que por cada tipo de sede se puede obtener el numero de camas disponibles, pero para cumplir con la columna de camas en mantenimiento se selecciona un numero aleatorio entre 0 y el 10% del numero de camas (parametro arbitrario).

En el caso de FAR_DISPENSACION escogemos un id_encuentro aleatorio, con esto tambien obtenemos pac_id y id_sede. Establecemos la fecha de dispensacion con fake como un aleatorio entre la fecha de inicio de atencion y la fecha de egreso, considerando que a los 3 dias de hospitalizado se le puede dar mas medicamento. El codigo de medicamento se escoge de un diccionario aleatoriamente, y con esto se puede obtener del mismo diccionario el nombre y vr unitario. La cantidad es un valor aleatorio de entre 1 y 3, ya que dificilmente se necesitaran mas de 3 presentaciones de un mismo medicamento, y en caso de que sea necesario se puede volver a dispensar. El tipo de prescripcion es un aleatorio entre magistral y oficial (de acuerdo con https://formulaslasalud.com/formulas-oficinales/) cargado mayormente hacia oficial en un 80%, ya que lo mas comun es comprar medicamentos ya preparados.

La tabla AGE_CITAS se poblo de manera similar a encuentros, con la diferencia de que la distribucion exponencial se utilizo para establecer la diferencia entre el registro de la cita y el inicio de la atencion. La hora de llegada del paciente puede ser anterior o posterior a la hora de la cita, ya que un paciente puede llegar tarde. Los estados de cita se establecieron como Agendada si la fecha programada es mayor a la fecha actual, cancelada si la persona llego a su cita despues del horario de atencion (hasta las 10 p.m. arbitrariamente ya que es la hora a la que cierra la mayoria de clinicas para consultas programadas) o atendida en cualquier otro caso.

El dag de generacion de insumos se encuentra dentro de un proyecto llamado "ssm-crudos" en la region us-central-1, asi como el resto de los elementos que se utilizaron en la prueba (composer, storage, etc.), ya que estos datos son los originales, aqui se realizara el resto de operaciones (correspondientes a las capas bronze, silver y gold) por motivos practicos, pero en un proyecto real lo ideal seria tener un proyecto para cada capa
En storage se guarda el bucket dependencias-ssm para guardar las dependencias como spark, faker o mysql.
ssm-crudos-data sera el bucket que contendra los datos generados en diferentes formatos, csv para tablas con pocos registros como la tabla de sedes, avro para registros con una cantidad considerable de datos como las camas y parquet para tablas como encuentros que contiene una gran cantidad de datos. ssm-workspaces contiene la ambientacion del proyecto (codigo de python del batch, su archivo de configuracion y archivo de configuracion del dag), el dag por su parte esta en el bucket del composer
